# Qloo: проверенные сведения и выводы

Дата проверки: 25 октября 2026 года.

## Исправления к `only me.txt`

Исходный пользовательский конспект сохранён без изменений. Он полезен как обзор,
но его примеры запросов и JSON нельзя использовать как API-контракт:

- API требует заголовок `X-Api-Key`, а не показанный в конспекте `Authorization`.
- `https://qloo.com` — сайт; API использует отдельные хосты. В рабочем проекте
  хакатонный ключ успешно проверен на `https://hackathon.api.qloo.com`.
- Поиск: GET `/search`, параметр `query`, а не `q`; результат содержит `results`
  со списком объектов и `entity_id`, а не примерные `data/id/ent_nike_12345`.
- Рекомендации: GET `/v2/insights`, `filter.type`, `signal.interests.entities`;
  ответ находится в `results.entities`, affinity — в `query.affinity` каждого объекта.
- GET принимает интересы как строку ID через запятую. WKT в Insights использует
  longitude перед latitude; радиус — метры. У `/search` геопараметры другие:
  `latitude,longitude` и радиус в милях. Их нельзя смешивать.
- `feature.explainability=true` добавляет вклад входных интересов в рекомендации.
  Отсутствие объяснения не обязательно означает ошибку рекомендаций.
- Утверждение конспекта о Webhooks не подтверждено изученными API-разделами;
  проект на него не опирается. Показатели масштаба и производительности
  из конспекта не использованы как гарантии для этого ключа.

## Реально проверено

Поиск Radiohead и получение мест в центрах Цюриха и Алматы работают.
В ответах есть числовые affinity в диапазоне 0–1, теги и explainability.
Примеры Цюриха: Cabaret Voltaire, ETH Zürich. Примеры Алматы: Synesthesia,
Masterskaya Space. Это результаты конкретного запроса, не постоянный список.

## Роль Qloo и LLM

Qloo связывает культурные интересы между категориями: например, артист/фильм → места.
Сам Qloo не выдаёт «лучший район для пары» в реализованном сценарии: приложение
считает эвристический компромисс поверх найденных мест. LLM только разбирает уточнения
и формулирует пояснение. При отсутствии его ключей всё работает через правила/шаблон.
Наличие культурной связи не доказывает, что конкретному человеку понравится район.

## Что можно развить дальше

1. Дать пользователю выбирать найденную сущность: Blade Runner может обозначать разные
   объекты; текущий автоматический выбор виден в шагах, но не подтверждается вручную.
2. Использовать настоящие полигоны районов вместо кругов и показывать отдельные места
   на карте с расстояниями и вкладом исходных интересов из explainability.
3. Получать теги через Lookup API и фильтровать категории на стороне Qloo.
   Сейчас исключения текстовые и применяются после получения первых 20 результатов:
   при жёстком фильтре подходящих мест может оказаться мало, даже если они есть в базе.
4. Сравнивать единый набор кандидатов с учётом контекста affinity и проверять устойчивость
   рейтинга при смене радиуса, количества мест и исключении одного интереса.
5. Разделить сценарии: выбор района для жизни, вечернего маршрута и путешествия.
   Для жилья отдельно нужны данные о бюджете, транспорте, доступности и реальном шуме.
6. Для публичного сервиса добавить авторизацию/квоты и общий кэш/ограничитель запросов
   между процессами. Текущая версия рассчитана на локальную демонстрацию.

Другие возможности официального API: рекомендации книг/кино/музыки/брендов,
географические heatmaps, аудитории, taste analysis, тренды и сравнение групп.
Они не реализованы в этом приложении; доступ конкретного ключа нужно проверять отдельно.

Документация описывает affinity с учётом контекста/нормализации запроса и отдельно
обсуждает близкие оценки. В статье про интерпретацию встречается представление 0–100;
в проверенных сырых ответах API используется 0–1. Собственная шкала приложения 0–100
вычисляется отдельно и не должна трактоваться как процент совпадения.
